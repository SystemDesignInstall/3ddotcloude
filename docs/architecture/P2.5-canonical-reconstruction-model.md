## 0. Purpose

This document answers a single architectural question:

> **What backend-independent spatial representation captures the result of any reconstruction backend in our platform?**

After C1-S1–S4 we proved that COLMAP can deliver a reconstruction through the platform's execution infrastructure. The provisional SparseModel JSON v1 served that purpose. But it is COLMAP-shaped: its fields mirror `cameras.bin / images.bin / points3D.bin`, its camera model vocabulary is a COLMAP-to-RFC-0009 mapping, and its pose convention follows COLMAP's (w,x,y,z) quaternion order remapped to (x,y,z,w).

If we build on top of this, COLMAP silently becomes the de facto data model. P2.5 defines the **canonical** model that any backend — COLMAP, SLAM, hybrid, or future — must express its results through.

---

## 1. Scope and Non-Goals

### In scope

1. Canonical entity definitions: `Reconstruction`, `ReconCamera`, `ReconImage`, `ReconPoint3D`, `ReconObservation`, `ReconTrack`
2. Coordinate frame convention for reconstruction results
3. Pose semantics: what `T_A_B` means, which direction, which frame
4. Provenance model: backend, configuration, inputs, execution, lineage
5. Uncertainty model: where uncertainty lives, what it means
6. Deterministic identity rules
7. Integration with existing `Scene`, `Frame`, `ImageObservation`, `CalibrationArtifact`, `GeometryElement`
8. Backend independence verification against COLMAP, SLAM, and a hypothetical future backend

### Non-goals (explicitly deferred)

| Deferred | Why |
|----------|-----|
| Actual C++ types and schemas | Design first, implement after approval |
| Worker protocol changes | No `input_kind` extension in this increment |
| Calibration pipeline | Separate architectural track (see §12) |
| Dense reconstruction | Sparse-only; dense is a downstream GeometryElement producer |
| SLAM implementation | Design reference only; no SLAM adapter exists |
| Loop closure / multi-session | Requires trajectory model first |
| AI/VGGT priors | Future backend consumer; out of M0 scope |
| Final schema file | Schema file creation is a P2.5 implementation step |

## 2. Architectural Position

### 2.1 Where Reconstruction lives in the platform

```
                    SPATIAL PLATFORM
                           │
                 ┌─────────┴─────────┐
                 │                   │
              Scene               Engine
            (domain)            (execution)
                 │                   │
                 │             Worker Protocol
                 │                   │
                 │          ProcessingAdapter
                 │                   │
                 │          Reconstruction Backend
                 │           (COLMAP / SLAM / ...)
                 │                   │
                 └─────────┬─────────┘
                           │
                 Canonical Reconstruction Model
                           │
                 ┌─────────┼──────────┐
                 ▼         ▼          ▼
            Scene Graph  Geometry   Quality
                        Graph       Report
```

The Canonical Reconstruction Model is the **output contract** of any reconstruction backend and the **input contract** for anything that consumes reconstructed geometry — scene update, geometry graph population, quality assessment, dense reconstruction, visualization.

### 2.2 Relationship to existing entities

```
CaptureSession
      │
      ├── Frame
      │     └── ImageObservation
      │
      ├── CalibrationArtifact
      │
      └── Reconstruction ──── (NEW: P2.5)
             │
             ├── ReconCamera[]
             ├── ReconImage[]
             ├── ReconPoint3D[]
             ├── ReconObservation[]
             └── ReconTrack[]
```

`Reconstruction` is a **child entity of a CaptureSession** (or a group of sessions for multi-session reconstruction). It does not replace `Scene`; it feeds data into the Scene's Observation Graph and Geometry Graph.

## 3. Canonical Entities

### 3.1 Reconstruction

The top-level container for one reconstruction result. A single session may produce multiple reconstructions (e.g. different backends, different configurations). A multi-session reconstruction references multiple sessions.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `reconstruction_id` | UUID | yes | Deterministic identity (§9) |
| `session_ids` | UUID[] | yes | One or more CaptureSession UUIDs that contributed images |
| `scene_id` | UUID | yes | Owning Scene |
| `coordinate_frame` | string | yes | Name of the reconstruction coordinate frame (§6) |
| `schema_version` | int | yes | Document schema version (currently 1) |
| `created_at_ns` | TimestampNs | yes | Creation time |
| `provenance` | Provenance | yes | Backend, config, inputs, execution (§8) |
| `status` | enum | yes | `reconstructing \| succeeded \| failed \| superseded` |

**Lifecycle:**

1. Backend is dispatched via worker protocol
2. Backend produces native output → converter → canonical document
3. Document is written as a `sparse_model` artifact (CAS)
4. Reconstruction entity is created in the scene (scene layer, not artifact)
5. Downstream consumers (quality, dense, visualization) read the reconstruction

**Backend independence:** COLMAP produces one reconstruction per run. SLAM produces incremental reconstructions that may be incrementally updated. A hybrid backend may fuse multiple sources. The `Reconstruction` entity is agnostic to this — it captures the result, not the process.

### 3.2 ReconCamera

One camera model as determined by the reconstruction. This is the **reconstruction's view** of the camera, which may differ from (and be informed by) the CalibrationArtifact.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `camera_id` | uint32 | yes | Backend-local camera ID (reconstruction-scoped, not global) |
| `width` | int64 | yes | Image width in pixels |
| `height` | int64 | yes | Image height in pixels |
| `intrinsic_model` | enum | yes | Canonical model vocabulary (§3.2.1) |
| `fx` | double | yes | Focal length x (pixels) |
| `fy` | double | yes | Focal length y (pixels) |
| `cx` | double | yes | Principal point x (pixels) |
| `cy` | double | yes | Principal point y (pixels) |
| `distortion_model` | enum | yes | Distortion type (§3.2.2) |
| `distortion_coefficients` | double[] | yes | May be empty for `none` |
| `calibration_ref` | UUID? | no | Reference to CalibrationArtifact if the reconstruction used an external calibration |

**Backend independence:** Every reconstruction backend must estimate or accept camera intrinsics. COLMAP estimates them from images; SLAM may accept them from a calibration file; a hybrid backend may refine them. The canonical model captures the result uniformly.

#### 3.2.1 Intrinsic model vocabulary

This vocabulary aligns with RFC-0009 §5 `calibration.schema.json` `intrinsic_model`:

| Model | Parameters | Notes |
|-------|------------|-------|
| `pinhole` | fx, fy, cx, cy | No distortion |
| `opencv` | fx, fy, cx, cy | + radial/tangential distortion |
| `opencv_fisheye` | fx, fy, cx, cy | + fisheye distortion |
| `fov` | fx, fy, cx, cy, omega | COLMAP FOV model |
| `omnidirectional` | fx, fy, cx, cy | Omni-directional |
| `custom` | fx, fy, cx, cy | + vendor-specific distortion |

**Rule:** `intrinsic_model` names the **projection model**, not the distortion model. Distortion is always a separate field. This separation is what allows a backend to use one distortion model during reconstruction and a different one for export.

#### 3.2.2 Distortion model vocabulary

| Model | Coefficients | Notes |
|-------|-------------|-------|
| `none` | [] | No distortion |
| `opencv_radial` | [k1, k2, p1, p2, k3?] | Brown-Conrady radial + tangential |
| `opencv_fisheye` | [k1, k2, k3, k4] | Division model |
| `equidistant` | [k1, k2, k3, k4] | Equidistant fisheye |
| `custom` | [...] | Vendor-specific |

**Alignment with calibration.schema.json:** The distortion vocabulary here is a superset of `calibration.schema.json` `distortion.model`. The reconstruction's distortion is always the one **actually used during reconstruction**, which may differ from the calibration's declared model.

### 3.3 ReconImage

One image as placed in the reconstruction. Each ReconImage references exactly one ReconCamera and one Frame.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `image_id` | uint32 | yes | Backend-local image ID (reconstruction-scoped) |
| `camera_id` | uint32 | yes | Reference to ReconCamera.camera_id |
| `frame_id` | UUID | yes | Reference to Frame (the kinematic frame from import) |
| `name` | string | yes | Original filename or identifier (provenance, not identity) |
| `pose` | ReconPose | yes | Camera pose in the reconstruction frame (§3.4) |
| `detected` | bool | yes | Whether this image was successfully registered |

**Backend independence:** COLMAP marks unregistered images. SLAM may drop images from the trajectory. Both map to `detected = false`. The `frame_id` link is the bridge to the platform's import model — it connects the reconstruction result back to the original `Frame` → `ImageObservation` → `ImageArtifact`.

### 3.4 ReconPose

The pose of a camera (or any rigid body) in the reconstruction coordinate frame. This is the **only** place where pose semantics are defined in the reconstruction model.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `rotation_xyzw` | double[4] | yes | Quaternion in platform convention: (x, y, z, w), scalar-last, right-handed |
| `translation_xyz` | double[3] | yes | Translation vector |

#### 3.4.1 Transform notation (normative)

Throughout this document, `T_A_B` denotes a rigid transform that maps a point **from frame B into frame A**:

```
p_A = T_A_B.rotation * p_B + T_A_B.translation
```

This is the standard robotics/computer-vision notation. It composes left-to-right:

```
T_A_C = T_A_B * T_B_C
```

meaning: first map from C to B, then from B to A.

#### 3.4.2 Canonical pose convention

The canonical pose stored in `ReconImage.pose` is:

```
T_reconstruction_camera : SE(3)
```

Meaning: transforms a point from **camera frame** to **reconstruction frame**:

```
p_reconstruction = T_reconstruction_camera.rotation * p_camera
                 + T_reconstruction_camera.translation
```

**Critical distinction — reconstruction frame ≠ project world frame:**

The reconstruction frame is a **local, arbitrary** coordinate system chosen by the backend (§5.1). It is NOT the project's `project_world` frame unless alignment has been explicitly performed. Therefore:

```
T_reconstruction_camera  ≠  T_world_camera   (in general)
```

They are equal **only after alignment**:

```
T_world_camera = T_world_reconstruction * T_reconstruction_camera
```

where `T_world_reconstruction` is the alignment transform stored in the FrameGraph edge between `project_world` and `reconstruction_*` (§5.2).

**Why this direction:** This is the standard in both COLMAP and most SLAM systems. COLMAP stores `qvec (w,x,y,z)` and `tvec` as the transformation from camera to world (its local world = reconstruction frame); ORB-SLAM stores the same. The canonical model standardizes on (x,y,z,w) quaternion order per ADR-007.

#### 3.4.3 Relationship to existing types

The existing `WorldFromCamera` strong type in `core/geometry/camera_transform.h` has the **same mathematical structure** as `T_reconstruction_camera` — both are SE(3) transforms from camera to some reference frame. However, the **semantic meaning** differs:

| Type | Semantics | Reference frame |
|------|-----------|----------------|
| `WorldFromCamera` | Transform from camera to **project world** | `project_world` |
| `T_reconstruction_camera` | Transform from camera to **reconstruction local frame** | `reconstruction_*` |

**Implementation rule:** When writing the reconstruction result into the FrameGraph, the adapter creates a `WorldFromCamera` for the edge `reconstruction_* → camera_*`. This is semantically correct because the "world" in `WorldFromCamera` is the **parent frame in the graph** — which is `reconstruction_*`, not `project_world`. The strong type name refers to the graph relationship, not to the project-level world frame.

```
FrameGraph edge:  reconstruction_0 → camera_i
Type:             WorldFromCamera   (parent from child)
Meaning:          T_reconstruction_camera
```

This is consistent with the existing usage in `core/geometry/camera_transform.h` where `WorldFromCamera` means "from camera frame to whatever frame is the parent" — the "World" in the name is the graph parent, not necessarily the project world.

**COLMAP mapping:** COLMAP stores `(qvec_wxyz, tvec)` as `T_world_camera` (COLMAP's "world" = reconstruction frame). The converter swaps quaternion components from (w,x,y,z) → (x,y,z,w) per ADR-007 and stores as `T_reconstruction_camera`. This is already implemented in `colmap_converter.cpp`.

**SLAM mapping:** ORB-SLAM stores `Tcw` (camera-from-world, where "world" = SLAM map frame). The conversion is `T_reconstruction_camera = Tcw.Inverse()`. The canonical model always stores the from-camera form.

### 3.5 ReconPoint3D

One reconstructed 3D point.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `point3d_id` | uint64 | yes | Backend-local point ID (reconstruction-scoped) |
| `xyz` | double[3] | yes | Position in the reconstruction coordinate frame (meters) |
| `color` | uint8[3] | yes | RGB color (estimated or from image) |
| `error` | double | yes | Mean reprojection error across observations (pixels) |
| `track_length` | int | yes | Number of observations (= track.size) |
| `track` | ReconObservation[] | yes | Observations of this point from images |

**Backend independence:** COLMAP stores points in `points3D.bin` with the same structure. SLAM stores landmarks in its own format. Both produce a position, color, error estimate, and a set of observations. The canonical model captures all of these.

**Uncertainty:** The `error` field (reprojection error) is the most basic quality indicator. Richer uncertainty (covariance, confidence) is deferred to the Uncertainty Model (§8) and the GeometryElement uncertainty block.

### 3.6 ReconObservation

One observation of a ReconPoint3D from a ReconImage. This is the atomic measurement that links a 3D point to a 2D feature.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `image_id` | uint32 | yes | Reference to ReconImage.image_id |
| `point2d_idx` | int | yes | Index of the 2D keypoint in the image's feature list |

**Why this is minimal:** The observation carries only the link. The 2D keypoint coordinates live in the `FeatureArtifact` for that image (already part of the platform via RFC-0007). This avoids duplicating feature data in the reconstruction document.

**FeatureArtifact bridge:**

```
ReconObservation
      │
      ├── image_id → ReconImage
      │                   │
      │                   └── frame_id → Frame
      │                                      │
      │                                      └── ImageObservation.artifact_ref → ImageArtifact
      │
      └── point2d_idx → FeatureArtifact.keypoints[point2d_idx]
                              │
                              └── (x, y) in pixel coordinates
```

This is the same bridge that RFC-0007 already established for feature extraction. The reconstruction simply adds the 3D association.

### 3.7 ReconTrack (synthesized)

A track is not a separate entity in the document but is **synthesized** from ReconPoint3D.track:

```
Track = {
    point3d_id: uint64,
    observations: ReconObservation[]
}
```

**Convention:** A track has at minimum 2 observations (otherwise the point is not triangulated). The platform may enforce a minimum track length for quality filtering, but the reconstruction model itself does not reject tracks with length 1 — that is a quality gate concern.

**Track identity:** The track's identity is the `point3d_id` it belongs to. There is no separate track UUID. This is because a track is an intrinsic property of a 3D point — it IS the point's observation history.

## 4. Document Structure

The canonical reconstruction document is a single JSON document that carries all entities. It is the content of a `sparse_model` artifact (CAS payload).

### 4.1 Top-level structure

```json
{
  "schema_version": 2,
  "reconstruction_id": "uuid",
  "session_ids": ["uuid", ...],
  "scene_id": "uuid",
  "coordinate_frame": "reconstruction_0",
  "status": "succeeded",
  "created_at_ns": 1234567890,
  "provenance": { ... },
  "cameras": [ ... ],
  "images": [ ... ],
  "points3D": [ ... ]
}
```

**Why schema_version 2:** The current provisional v1 (from C1-S4) uses `schema_version: 1`. The canonical model introduces structural changes (see §4.2), so it starts at version 2. The v1→v2 transition is a clean break: v1 was COLMAP-shaped, v2 is backend-independent.

### 4.2 Differences from provisional v1

| Aspect | v1 (provisional) | v2 (canonical) |
|--------|-------------------|----------------|
| Camera model | COLMAP model name + RFC-0009 mapping | Backend-independent `intrinsic_model` + `distortion_model` |
| Distortion | Not carried | Explicit `distortion_model` + `distortion_coefficients` |
| Pose convention | Remapped from COLMAP (w,x,y,z) | Platform-native (x,y,z,w) per ADR-007 |
| Calibration reference | None | Optional `calibration_ref` linking to CalibrationArtifact |
| Provenance | Artifact manifest only | Dedicated `provenance` block in the document |
| Reconstruction identity | Implicit (artifact UUID) | Explicit `reconstruction_id` (deterministic, §9) |
| Session binding | None | Explicit `session_ids` |
| Frame binding | None | Each image carries `frame_id` |
| Coordinate frame | Implicit | Explicit `coordinate_frame` string |
| Point error | Mean reprojection error | Mean reprojection error + optional per-axis uncertainty |
| Status | None | `succeeded / failed / superseded` |

## 5. Coordinate Frames (normative)

### 5.1 Reconstruction coordinate frame

Every reconstruction defines its own coordinate frame. The frame name is a string identifier (not a UUID) that is:

- **Unique within the reconstruction** — different reconstructions may use the same name with different semantics
- **Assigned by the backend** — COLMAP calls it "world"; SLAM may call it "map"; the platform calls it by the name the backend provides, prefixed with `reconstruction_`
- **Arbitrary origin and orientation** — the backend chooses the coordinate system; the platform does not enforce a particular convention (no mandatory ENU/NED)
- **Right-handed, meters** — per ADR-007, all spatial coordinates are in meters and right-handed frames

**COLMAP mapping:** COLMAP's reconstruction coordinate frame is arbitrary (depends on the random seed and data). The converter names it `reconstruction_0` (or `reconstruction_<id>`).

**SLAM mapping:** SLAM's map frame is typically anchored to the first frame or to an IMU frame. The converter names it `reconstruction_0`.

### 5.2 Frame graph integration

The reconstruction coordinate frame becomes a node in the scene's `FrameGraph`:

```
project_world (root)
    │
    ├── reconstruction_0
    │     ├── camera_0
    │     ├── camera_1
    │     └── ...
    │
    ├── reconstruction_1  (second backend result)
    │     └── ...
    │
    └── trajectory_0  (SLAM trajectory, future)
          └── ...
```

The `parent_from_child` transform between `project_world` and `reconstruction_0` is:

- **Identity** if the reconstruction is in the project's world frame (e.g. after georeferencing)
- **An alignment transform** if the reconstruction needs to be registered to the project frame
- **Unknown** (identity placeholder) until alignment is performed

**Rule:** The reconstruction does not assume georeferencing. It produces geometry in its own frame. Alignment to `project_world` is a separate pipeline stage (the "align" stage in `reconstruction-pipeline.md`).

### 5.3 Camera frame

Each camera has its own coordinate frame. The standard OpenCV convention applies (per `coordinate-systems.md`):

```
X → right
Y → down
Z → forward (optical axis)
```

This is the frame that `T_reconstruction_camera` maps **from**. It is the camera's local coordinate system.

### 5.4 Multi-backend frame alignment

When two backends produce reconstructions of the same scene, they produce different `reconstruction_*` frames. Alignment between them is a downstream operation:

```
reconstruction_colmap ──T_align──→ reconstruction_slam
```

Or both aligned to `project_world`:

```
reconstruction_colmap ──T_1──→ project_world
reconstruction_slam   ──T_2──→ project_world
```

The Canonical Model does not perform this alignment. It provides the data that makes alignment possible.

## 6. Pose Semantics (normative)

### 6.1 Transform direction

The canonical pose stored in `ReconImage.pose` is:

```
T_reconstruction_camera : SE(3)
```

Transform notation follows §3.4.1: `T_A_B` maps points from frame B into frame A.

```
p_reconstruction = T_reconstruction_camera.rotation * p_camera
                 + T_reconstruction_camera.translation
```

**This is NOT `T_world_camera`.** The reconstruction frame is a local coordinate system (§5.1). Only after alignment to `project_world` does `T_world_camera` become available:

```
T_world_camera = T_world_reconstruction * T_reconstruction_camera
```

### 6.2 Derivation from COLMAP

COLMAP stores `(qvec_wxyz, tvec)` where:
- `qvec` is the rotation quaternion in (w, x, y, z) order
- `tvec` is the translation vector
- Together they define `T_world_camera` (COLMAP's "world" = reconstruction frame)

The converter:
1. Swaps qvec from (w, x, y, z) → (x, y, z, w) per ADR-007
2. Stores as `rotation_xyzw` and `translation_xyz`
3. The result is `T_reconstruction_camera`, usable as `WorldFromCamera` in the FrameGraph context (§3.4.3)

### 6.3 Derivation from SLAM (future)

ORB-SLAM stores `Tcw` (camera-from-world, where "world" = SLAM map frame):
```
T_reconstruction_camera = Tcw.Inverse()
```

This is a backend-specific conversion that happens inside the SLAM adapter/converter, not in the canonical model.

### 6.4 Derivation from hybrid/future

A hybrid backend may produce fused poses from multiple sources. The canonical model does not care how they were computed — it stores the result as `T_reconstruction_camera` per image.

### 6.5 Strong type mapping

```
ReconPose.rotation_xyzw + translation_xyz
    ≡
SE3(Quaternion(x,y,z,w), [tx,ty,tz])
    ≡
T_reconstruction_camera
    (reconstruction's local frame, NOT project_world)
```

In the FrameGraph, when stored as an edge `reconstruction_* → camera_*`:

```
WorldFromCamera(T_reconstruction_camera)
    (semantic: "parent_from_child" where parent = reconstruction_*)
```

The `WorldFromCamera` strong type is reused because its mathematical structure is identical — SE(3) from camera to some parent frame. The parent frame in the graph is `reconstruction_*`, not `project_world`.

## 7. Calibration Integration

### 7.1 Separation of concerns

```
CalibrationArtifact              Reconstruction
  (input authority)                (result)
        │                              │
        ├── intrinsics                 ├── ReconCamera.intrinsics
        ├── distortion                 ├── ReconCamera.distortion
        ├── extrinsics                 │   (reconstruction-estimated)
        └── uncertainty                └── ReconCamera.calibration_ref
                                            (optional link)
```

**CalibrationArtifact** is the **declared** calibration of a sensor — measured, imported, or estimated by a calibration tool. It is the authority on what the camera's intrinsics ARE.

**ReconCamera** contains the intrinsics **as used by the reconstruction backend**. These may differ from the calibration because:
- The backend may refine intrinsics during bundle adjustment
- The backend may use a different distortion model than the calibration declares
- The backend may have no calibration input and estimated everything from scratch

**The link:** `ReconCamera.calibration_ref` (optional UUID) points to the CalibrationArtifact that was used as input (if any). This preserves provenance without enforcing identity.

### 7.2 COLMAP behavior

COLMAP can operate in two modes:
1. **No calibration input:** Estimates all intrinsics from images → `calibration_ref = null`
2. **With camera model file:** Uses a predefined camera model → `calibration_ref` points to the CalibrationArtifact (if the adapter wrote one)

### 7.3 SLAM behavior (future)

SLAM systems typically accept calibration as input and may refine it. The reconstruction stores the final values; `calibration_ref` points to the input CalibrationArtifact.

### 7.4 Rule

> A backend that refines intrinsics stores the refined values in ReconCamera and links the source calibration via `calibration_ref`. The CalibrationArtifact is never mutated by the reconstruction.

## 8. Provenance Model

### 8.1 Provenance block

Every reconstruction document carries a provenance block:

```json
{
  "provenance": {
    "backend": {
      "name": "colmap",
      "version": "3.13",
      "adapter_version": "0.1.0"
    },
    "configuration_hash": "sha256:...",
    "input_artifact_hashes": ["sha256:...", ...],
    "engine_version": "0.1.0",
    "engine_commit": "abc1234",
    "git_commit": "def5678",
    "started_at_ns": 1234567890,
    "finished_at_ns": 1234567900,
    "duration_ns": 10000000000,
    "backend_specific": { ... }
  }
}
```

| Field | Description |
|-------|-------------|
| `backend.name` | Canonical backend identifier (never a path or binary name) |
| `backend.version` | Backend version string |
| `backend.adapter_version` | Our adapter version |
| `configuration_hash` | SHA-256 of the effective configuration (per ADR-020) |
| `input_artifact_hashes` | CAS hashes of all input artifacts (images, calibration) |
| `engine_version` | Spatial Platform engine version |
| `engine_commit` | Engine git commit |
| `git_commit` | Adapter git commit |
| `started_at_ns` | Reconstruction start time |
| `finished_at_ns` | Reconstruction end time |
| `duration_ns` | Wall-clock duration |
| `backend_specific` | Arbitrary backend-specific metadata (free-form JSON) |

**Backend independence:** The `backend` block identifies the producer without coupling the model to any specific backend. The `backend_specific` field carries backend-specific metadata (e.g. COLMAP's number of registered images, SLAM's keyframe count) without polluting the canonical fields.

### 8.2 Lineage chain

```
ImageArtifact[] ─────────────────────┐
                                     │
CalibrationArtifact? ────────────────┤
                                     │
Configuration (effective JSON) ──────┤
                                     │
                                     ▼
                            Reconstruction Provenance
                                     │
                                     ▼
                          sparse_model artifact (CAS)
                                     │
                                     ▼
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
               Scene Graph    Geometry Graph    Quality Report
```

Every artifact in this chain carries its own provenance. The reconstruction provenance specifically records which input artifacts were consumed, enabling:
- **Reproducibility:** Same inputs + same config + same backend = same output (ADR-020)
- **Traceability:** Any downstream artifact can trace back to its source images
- **Invalidation:** If an input artifact changes, the reconstruction cache is invalidated (ADR-020 task cache)

## 9. Deterministic Identity

### 9.1 Reconstruction identity

| Entity | Identity | Deterministic? | Scope |
|--------|----------|---------------|-------|
| `Reconstruction` | `reconstruction_id` (UUID) | No — instance identity | Project-wide |
| `ReconCamera` | `camera_id` (uint32) | No — backend-local | Reconstruction-scoped |
| `ReconImage` | `image_id` (uint32) | No — backend-local | Reconstruction-scoped |
| `ReconPoint3D` | `point3d_id` (uint64) | No — backend-local | Reconstruction-scoped |
| `ReconObservation` | (image_id, point2d_idx) | Implicit | Reconstruction-scoped |
| SparseModel artifact | `content_hash` (SHA-256) | Yes — content-addressed | CAS-wide |

### 9.2 Why reconstruction IDs are not deterministic

A reconstruction is an **instance** — it captures one specific execution with one specific configuration and one specific random seed (if applicable). Two identical runs of the same backend may produce different internal IDs. The reconstruction's identity is assigned at creation, not derived from content.

**Contrast with Frame/Observation:** Frame and Observation IDs are deterministic (UUIDv5) because they represent **immutable facts about captured data** — the same sensor, timestamp, and content always produce the same entity. A reconstruction is an **analysis result**, not a raw measurement.

### 9.3 Artifact deduplication

While the reconstruction ID is not deterministic, the **artifact** produced by the converter IS content-addressed. Two identical reconstructions (same inputs, same config, same backend) produce the same `content_hash` and deduplicate in the CAS (ADR-010). The `reconstruction_id` inside the document may differ, but the CAS payload is identical.

### 9.4 Backend-local ID mapping

Backend-local IDs (camera_id, image_id, point3d_id) are integers scoped to one reconstruction. They carry no meaning outside the document. Cross-reconstruction ID mapping (e.g. "camera 1 in COLMAP = camera 3 in SLAM") is done via `frame_id` (for images) and `calibration_ref` (for cameras).

## 10. Uncertainty Model

### 10.1 Where uncertainty lives

Uncertainty in the reconstruction model is **layered**:

| Layer | What | Where |
|-------|------|-------|
| **Per-point** | Reprojection error | `ReconPoint3D.error` (always present) |
| **Per-point** | 3D covariance | `ReconPoint3D.uncertainty` (optional, §10.2) |
| **Per-image** | Pose uncertainty | `ReconImage.pose_uncertainty` (optional, §10.3) |
| **Per-camera** | Intrinsics uncertainty | Via `CalibrationArtifact.uncertainty` (existing, RFC-0009) |
| **Per-observation** | Feature uncertainty | Via `FeatureArtifact.keypoints[].response` (existing, RFC-0007) |
| **Global** | Reconstruction quality | Via `QualityReport` (existing, RFC-0005) |

### 10.2 Per-point uncertainty (optional extension)

```json
{
  "uncertainty": {
    "covariance_xyz": [double[6]],
    "confidence": 0.95,
    "source_count": 12
  }
}
```

| Field | Description |
|-------|-------------|
| `covariance_xyz` | 3×3 symmetric covariance matrix in reconstruction frame (flattened row-major: [σxx, σxy, σxz, σyy, σyz, σzz]) |
| `confidence` | [0, 1] — posterior confidence from bundle adjustment |
| `source_count` | Number of images observing this point (= track length) |

**Not all backends produce covariance.** The field is optional. When present it enables downstream accuracy assessment. When absent, the reprojection `error` is the only quality indicator.

### 10.3 Per-image pose uncertainty (optional extension)

```json
{
  "pose_uncertainty": {
    "translation_covariance": [double[6]],
    "rotation_covariance": [double[6]]
  }
}
```

Both are 3×3 symmetric covariance matrices flattened row-major. These are the diagonal blocks of the full SE(3) covariance from bundle adjustment.

### 10.4 Integration with GeometryElement uncertainty

The `GeometryElement` schema already defines an uncertainty block:

```json
{
  "uncertainty": {
    "confidence": 0.9,
    "source_count": 12,
    "residual": 0.23
  }
}
```

When a reconstruction point is exported to the Geometry Graph, the per-point uncertainty from the reconstruction maps to this block. The mapping is:

| Reconstruction | GeometryElement |
|---------------|-----------------|
| `error` | `residual` |
| `source_count` | `source_count` |
| `confidence` | `confidence` |
| `covariance_xyz` | Stored in a separate uncertainty artifact (too large for inline) |

### 10.5 Reconstruction QA integration

The QualityReport (RFC-0005) consumes reconstruction data to produce quality metrics:

```
Reconstruction
      │
      ├── reprojection_error (from ReconPoint3D.error)
      ├── track_length_distribution
      ├── camera_residuals (from per-camera reprojection errors)
      ├── registered_image_ratio
      └── point_density
              │
              ▼
        QualityReport
```

This is the natural integration point for quality assessment — the reconstruction model provides the raw data, the QualityReport aggregates it into actionable metrics.

## 11. Backend Independence Verification

### 11.1 COLMAP

| COLMAP concept | Canonical model | Conversion |
|----------------|----------------|------------|
| `cameras.bin` | `ReconCamera[]` | Model ID → `intrinsic_model` + `distortion_model`; params → fx/fy/cx/cy + coefficients |
| `images.bin` | `ReconImage[]` | qvec(w,x,y,z) → `rotation_xyzw(x,y,z,w)`; tvec → `translation_xyz`; name → `name` (provenance) |
| `points3D.bin` | `ReconPoint3D[]` | xyz → `xyz`; rgb → `color`; error → `error`; track → `track` |
| COLMAP world frame | `coordinate_frame: "reconstruction_0"` | Assigned by converter |
| COLMAP camera_id | `ReconCamera.camera_id` | Direct mapping (uint32) |
| COLMAP image_id | `ReconImage.image_id` | Direct mapping (uint32) |
| COLMAP point3D_id | `ReconPoint3D.point3d_id` | Direct mapping (uint64) |

**Provenance:** `backend.name = "colmap"`, `backend.version = "3.13"`.

### 11.2 SLAM (ORBSLAM-like)

| SLAM concept | Canonical model | Conversion |
|--------------|----------------|------------|
| Camera intrinsics | `ReconCamera[]` | K matrix → fx/fy/cx/cy; distortion model → `distortion_model` |
| Keyframe poses | `ReconImage[]` (detected=true) | Tcw → Inverse → `pose` (T_reconstruction_camera) |
| Landmarks | `ReconPoint3D[]` | position → `xyz`; descriptor → not stored (see below) |
| Covisibility graph | Not directly in model | Captured in `provenance.backend_specific` |
| Map frame | `coordinate_frame: "reconstruction_0"` | Named by adapter |
| IMU frame | Separate `CoordinateFrame` node | If sensor fusion, extrinsics in CalibrationArtifact |

**Track reconstruction:** SLAM's landmark observations are reconstructed from the keyframe-landmark association matrix. Each association becomes a `ReconObservation(image_id, point2d_idx)`. The 2D keypoint coordinates are stored in a FeatureArtifact for the corresponding Frame, linked via `frame_id`.

**Incremental updates:** SLAM may produce partial reconstructions that grow over time. Each snapshot is a complete `Reconstruction` document. The `status` field distinguishes `reconstructing` (in progress) from `succeeded` (final).

### 11.3 Hybrid / future backend

A hybrid backend that fuses COLMAP + SLAM + additional sensors:

| Hybrid concept | Canonical model |
|----------------|----------------|
| Fused cameras | `ReconCamera[]` (possibly merged from multiple sources) |
| Fused poses | `ReconImage[]` (with refined poses from fusion) |
| Fused points | `ReconPoint3D[]` (with cross-validated observations) |
| Source attribution | `provenance.backend_specific.sources` |

The canonical model does not need to know about fusion. It stores the result. The `provenance` block records which backends contributed.

### 11.4 AI priors (VGGT-like)

An AI-based reconstruction produces:
- Camera poses (possibly rough)
- Point positions (possibly sparse)
- Confidence maps

These map directly:
- Poses → `ReconImage.pose` (with low confidence annotation)
- Points → `ReconPoint3D` (with high uncertainty)
- Confidence → `ReconPoint3D.uncertainty.confidence`

The key principle: **AI outputs are priors, not authoritative** (Architecture Principle 7). The `provenance.backend.name` identifies the AI system; downstream consumers decide how to weight it.

### 12.2 Bridge: Reconstruction → Scene

The reconstruction populates the scene via these write operations:

| Write | Target | Trigger |
|-------|--------|---------|
| `Frame.pose_ref` | Frame | After reconstruction: the reconstructed pose links back to the import frame |
| CoordinateFrame nodes | FrameGraph | Reconstruction frame + camera frames |
| GeometryElement nodes | GeometryGraph | 3D points exported as Point elements |
| FeatureSet associations | ObservationGraph | Track data links observations to 3D points |

**The reconstruction does NOT own Frames or Observations.** Frames exist from import. Observations exist from import and feature extraction. The reconstruction **associates** them — it adds 3D geometry to existing 2D data.

### 12.3 Artifact flow

```
Import:     Image file → ImageArtifact (CAS) + Frame + ImageObservation
Features:   ImageArtifact → FeatureArtifact (CAS)
Calibration: Sensor record → CalibrationArtifact (CAS)
Reconstruction: ImageArtifact[] + CalibrationArtifact? → sparse_model artifact (CAS)
                │
                └── sparse_model contains Reconstruction document
                      (cameras, images with poses, points with tracks)
```

Each artifact is content-addressed (CAS). The reconstruction artifact's `content_hash` is the ADR-020 cache key for the entire reconstruction.

## 13. Deterministic Serialization

### 13.1 Canonical JSON rules

The reconstruction document serializes to JSON with these rules (matching ADR-020 determinism requirements):

1. **Field order:** Fixed (not dependent on insertion order). Cameras sorted by `camera_id`, images sorted by `image_id`, points sorted by `point3d_id`.
2. **Number format:** nlohmann shortest round-trip (already used in `colmap_converter.cpp`).
3. **No timestamps:** The document carries `created_at_ns` and `provenance` timestamps, but no random or current-time values.
4. **No UUIDs in numeric fields:** Backend-local IDs are integers; reconstruction_id is a UUID.
5. **Array elements:** Ordered by ID; no set semantics.

### 13.2 Determinism guarantee

```
Same backend + Same inputs + Same config + Same engine version
    ⟹
    Identical bytes (content_hash)
```

This is the ADR-020 contract. The canonical model maintains it by:
- Sorting all collections by ID
- Using deterministic number formatting
- Excluding non-deterministic values from the document body
- Carrying execution identity in the `provenance` block (which IS different per run but does not affect the cache key — the cache key uses `configuration_hash` + `input_artifact_hashes`, not timestamps)

**Note:** The `provenance.started_at_ns` and `provenance.git_commit` fields make the full document non-deterministic across runs. The **cache key** is computed from a stable subset (inputs + config + backend version + engine version), not from the full document. This matches the existing ADR-020 task cache behavior.

## 14. Normative Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| **D-CRM-01** | The canonical pose convention is `T_reconstruction_camera : SE(3)`, mapping points from camera frame to the reconstruction's local frame. This is NOT `T_world_camera` unless alignment has been performed. | Mathematical precision; avoids ambiguity between reconstruction-local and project-world frames. Alignment is a separate pipeline stage. |
| **D-CRM-02** | Quaternion order is (x, y, z, w) scalar-last per ADR-007 | Platform-wide convention; no exceptions for backend outputs |
| **D-CRM-03** | Backend-local IDs (camera_id, image_id, point3d_id) are scoped to one Reconstruction document | No global ID space for reconstruction entities; cross-reconstruction mapping uses Frame/Calibration refs |
| **D-CRM-04** | Distortion model is a separate field from projection model | Allows backends to use different distortion models during reconstruction vs. calibration |
| **D-CRM-05** | `calibration_ref` is optional and does not imply that intrinsics are identical | Backends may refine intrinsics; the link is for provenance, not constraint |
| **D-CRM-06** | Coordinate frame name is assigned by the adapter, prefixed with `reconstruction_` | Backend-specific naming is pushed to the adapter layer; the model requires only a string identifier |
| **D-CRM-07** | Reconstruction identity (`reconstruction_id`) is instance-scoped (random UUIDv4), not deterministic | A reconstruction is an execution result, not a content-derived fact |
| **D-CRM-08** | Per-point uncertainty is optional; reprojection error is always present | Not all backends produce covariance; the model degrades gracefully |
| **D-CRM-09** | Observations reference FeatureArtifact keypoints by index, not by coordinate duplication | Avoids data duplication; FeatureArtifact is the single source of truth for 2D keypoints |
| **D-CRM-10** | The schema_version transitions from 1 (provisional) to 2 (canonical) | Clean break from COLMAP-shaped v1 to backend-independent v2 |
| **D-CRM-11** | `provenance.backend_specific` carries arbitrary backend metadata | Prevents backend-specific fields from polluting the canonical model |
| **D-CRM-12** | Multi-session reconstruction uses `session_ids: UUID[]` | Supports SLAM-style multi-session and future map-merging |
| **D-CRM-13** | Transform notation: `T_A_B` maps points from frame B into frame A (§3.4.1). `WorldFromCamera` is used in the FrameGraph as `parent_from_child` where parent is the graph parent — which may be `reconstruction_*`, not `project_world`. | Establishes consistent mathematical language; resolves ambiguity between the strong type name and the actual reference frame |
| **D-CRM-14** | `T_reconstruction_camera ≠ T_world_camera` in general. They are equal only after alignment: `T_world_camera = T_world_reconstruction * T_reconstruction_camera`. | Prevents silent assumption that reconstruction output is in the project world frame |
| **D-CRM-15** | Reconstruction is **both** a scene entity (SQLite row) and an artifact (CAS payload). The scene row carries metadata for queries; the CAS payload carries the full document. Mirrors the CalibrationArtifact pattern (CalibrationRow + CAS). | Enables query consumers to access status/metadata without reading multi-MB payloads; supports FrameGraph node identity and Frame.pose_ref resolution |
| **D-CRM-16** | `ReconTrack` is synthesized from `ReconPoint3D.track[]`, not a separate entity. A track IS a point's observation history. | Avoids redundant storage, extra JOINs, and consistency risks. The atomic unit is `ReconObservation`; the track is the collection per point. |
| **D-CRM-17** | Backend-local IDs remain scoped to one Reconstruction document. No global UUID mapping at reconstruction time. Cross-reconstruction linking uses `frame_id` (images) and `calibration_ref` (cameras). | Premature optimization to add UUID mapping now; the existing linking mechanism is sufficient. Global UUID mapping can be added later if multi-reconstruction fusion requires it. |
| **D-CRM-18** | The reconstruction document references existing FeatureArtifacts (produced by feature extraction, RFC-0007), not its own copies. `ReconObservation.point2d_idx` indexes into `FeatureArtifact.keypoints[]` via the `frame_id → Frame → FeatureSet → FeatureArtifact` chain. | Single source of truth for 2D keypoints; avoids data duplication and consistency risk. |
| **D-CRM-19** | Each SLAM snapshot is a new `Reconstruction` with a new `reconstruction_id`. Status field distinguishes `reconstructing` (in progress) from `succeeded` (final) from `superseded` (overtaken by a newer snapshot). The latest `succeeded` reconstruction is the active one. | Matches the instance identity model (§9.2); preserves full history; avoids mutable state in an append-only model. |
| **D-CRM-20** | All input images are included in `ReconImage[]`, with `detected=false` for unregistered images. Consumers filter by `detected=true` when they only want registered images. | Preserves full input list for provenance; enables analysis of why images were not registered; matches COLMAP's native behavior. |
