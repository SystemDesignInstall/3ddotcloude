### REQUIRED: Separate Rotation/Direction From Metric Scale

The approved scale policy may use an **already metric, provenance-backed trajectory**. It does not require a new independent scale sensor on every loop, but it must not declare an arbitrary monocular trajectory metric.

Required data flow:

```text
CAS feature correspondences + resolved source/target camera calibration
  -> calibrated backend inference of relative R and translation direction
  -> cheirality/sign and canonical-frame validation
  -> unit direction in source-camera coordinates
  + existing metric trajectory and resolvable scale provenance
  -> ResolveMetricTranslationFromUnitDirection
  -> resolved metric LoopClosure measurement
  -> LoopClosureToPoseGraph -> TrajectoryOptimizer/GTSAM
```

The existing helper is `core/trajectory/pose_graph_helpers.h:487-543`:

```text
delta_p_W = p_target_W - p_source_W
t_hat_W   = R_W_source * t_hat_source
lambda    = dot(t_hat_W, delta_p_W)
t_metric_source = lambda * t_hat_source
cos_theta = dot(normalize(t_hat_W), normalize(delta_p_W)) >= 0.5
```

`lambda` has metres only if the trajectory already has metres. The function projects its displacement onto an independently estimated direction; it neither estimates that direction nor discovers absolute scale. It cannot establish independent scale-drift correction when the direction and prior displacement are collinear. Fixture expectations must respect that limitation.

There is no engine call to this helper today. `LoopClosureToPoseGraph` directly treats the closure's translation as resolved metres (`engine/pipeline/loop_closure_to_pose_graph.cpp:71-82`). Passing a unit Essential direction there would silently turn it into a one-metre edge.

### REQUIRED: Input and Frame Contract

- Resolve candidate source/target frame identities, timestamps and pinned FeatureArtifacts through existing host APIs; verify CAS bytes and preserve keypoint index ordering.
- Resolve the actual intrinsics, distortion and any rig transform valid for each frame. Intrinsics/distortion alone do not establish metres. An authenticated metric inter-camera baseline can establish scale when tied to the applicable sensor observations; a calibration record's presence alone is insufficient.
- Resolve trajectory nodes and `metric_basis.scale_calibration_ref` plus producer/configuration provenance. `ValidateMetricBasis` checks nonempty strings only (`core/trajectory/metric_basis.h:88-103`); that alone does not authenticate a scale-producing artifact.
- Consume a pre-existing metric basis such as validated odometry scale, calibrated baseline or metric alignment. A literal `declared=true` or a made-up calibration reference is insufficient. Ground-truth fixture data may establish test inputs explicitly, but must never be returned as the provider's estimated output.
- Honor the actual graph convention `T_source_target = inverse(T_W_source) * T_W_target`: target coordinates map into source coordinates, with translation expressed in the source frame (`core/trajectory/pose_graph_helpers.h:14-18,61-70`). A backend returning `X_target = R_ts * X_source + t_ts` requires inversion: `R_st = transpose(R_ts)`, `t_st = -transpose(R_ts) * t_ts`. Some existing comments name the opposite direction; tests must establish the convention before integration.
- Do not set `has_relative_pose=true` for an unresolved unit-direction result on the current public verification seam. The existing consumer interprets that result as metric. Resolve scale first, or explicitly design a separate adapter-private handoff; do not silently reinterpret frozen fields.

### GAP: Minimum Provider, Not a Fake Implementation

The smallest architectural fit is a calibrated adapter implementing the existing `GeometricVerifier`, supplied with immutable, host-resolved calibration and metric context. DB/CAS lookup stays on the host; only canonical values cross the adapter seam. No new Core schema or replacement of the optimizer interfaces is required by this candidate design.

The candidate backend implementation can reuse installed GTSAM Essential factors and LM. However, implementing that adapter still needs a specified and tested inference path: initialization, robust evidence selection, degeneracy handling, cheirality, translation sign and frame conversion. Availability of an LM solver does not prove those decisions. `EssentialMatrix::FromPose3` applied to the drifted trajectory is an initialization at most, never a measured closure.

**Provider implementation status: NOT PROVEN.** No fake provider, manually supplied result, new Essential estimator/decomposition, new scale source or rewritten 8a/8b/8c math was introduced in this phase. This is not a claim that a compliant adapter is impossible; its evidence-generating contract must be resolved and validated before Phase 2.

| Condition | Required outcome |
|---|---|

These are the required boundary checks, not claims that they are all implemented. The current edge builder does not explicitly test `has_relative_pose`; the direction resolver assumes unit input and does not authenticate metric basis. These must not be used as implicit validation shortcuts.

### GAP: Geometric Golden and BA

The BA adapter already evaluates actual geometry using `EvaluateReprojection` before and after the backend on the same supplied observations (`adapters/colmap/colmap_bundle_adjustment_adapter.cpp:149-154,277-298`). That is the evaluator to reuse, unchanged.

The current runner supplies no observations (`sparse_correction_runner.cpp:351-357`), the current golden uses hardcoded RMS in `StubOptimizer` (`tests/unit/test_p3_sparse_correction_pipeline.cpp:123-150`), and the existing BA probe shifts point x by 0.5 rather than optimizing (`tests/unit/colmap_probe_shim_main.cpp:240-247,296-305`). None is evidence for the required measured optimizer improvement.

The valid continuation needs pinned observed keypoints, real source/target calibration, a measured calibrated pose, real GTSAM trajectory optimization and an actual BA-capable adapter/probe. BA observations must be rebuilt from v3 tracks after retriangulation changes point IDs. A probe that emits a chosen transform or copies ground truth is not a measurement provider; one that reports chosen RMS is not an optimizer.
