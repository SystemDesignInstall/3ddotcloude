## 1. Objective

Execute and prove the complete sparse-correction chain through `Engine::RunPipeline("p3_sparse_correction", ...)`, with real calibrated measurement generation, existing geometry/optimizer seams, CAS and atomic revision transitions. Do not fabricate pose, scale, geometry, optimizer output or RMS improvement.

## 2. Previous Gap

The prior 670-test suite combined Engine dispatch with direct host-stage calls. The later 676-test subset moved commit/BA behind a registered runner but omitted LC, metric pose, GTSAM, feedback and retriangulation. Its BA stub supplies hardcoded RMS. Neither proves the full GO.

Phase 1 identifies an upstream dependency gap: the concrete Fundamental verifier returns no relative pose. See [metric-source contract](P3.1-production-sparse-correction-closure.md#6-phase-1-metric-source-contract-current) for inspected inputs, backend primitives, frame conventions, scale recovery and required rejection cases.

Engine::RunPipeline("p3_sparse_correction", ...)

## 6. Worker Boundary

DB reads/writes in the current subset are host-runner operations, not worker operations. Current architectural checks are recorded in section 21; they do not establish that missing stages execute or that the full chain is transactional. No backend or DB access was moved across a boundary in this audit.

## 7. Loop Closure Path

**NOT PROVEN.** The runner does not use `matcher` or `verifier`. `VerifyLoopClosureGeometry` is an existing lower-level orchestrator, but it copies the injected verifier's output rather than generating missing pose/scale (`engine/pipeline/loop_closure_verification.cpp:68-113`).

The only concrete verifier estimates Fundamental F and returns `has_relative_pose=false` (`adapters/visual_geometry/fundamental_verifier.cpp:303-375`). No calibrated provider is currently integrated. GTSAM Essential/LM primitives are an available candidate backend, not a proven provider. The phase gate remains held pending an inference contract covering calibration, initialization, inliers, degeneracy, sign and cheirality.

The existing `ResolveMetricTranslationFromUnitDirection` (`core/trajectory/pose_graph_helpers.h:487-543`) can project a **genuinely metric** trajectory displacement onto an independently inferred calibrated direction. It does not estimate that direction or create metric scale. No engine caller currently performs this handoff; `LoopClosureToPoseGraph` assumes the supplied translation is already in metres (`engine/pipeline/loop_closure_to_pose_graph.cpp:71-82`).

## 8. GTSAM Path

**NOT PROVEN through P3.1.** `GtsamTrajectoryOptimizer` exists behind `TrajectoryOptimizer`, but the runner never invokes it. Its lower-level tests consume supplied graph measurements, not measured loop closures from the P3.1 image path. Graph optimization cannot supply the missing calibrated verification measurement.

## 9. ApplyOptimizedTrajectory

**NOT PROVEN through P3.1.** The existing implementation (`core/trajectory/reconstruction_feedback.h:103-225`) is unchanged and not called by the runner. Continuation must resolve frame IDs, explicit trajectory-to-reconstruction alignment and successful optimization before invoking it. Missing image/frame associations cannot be counted as a successful correction.

## 10. Retriangulation

**NOT PROVEN through P3.1.** Frozen `core/geometry/triangulation.h:269-571` is not invoked. The runner supplies the committed source directly as `source_v3` (`sparse_correction_runner.cpp:351-357`); naming it v3 does not prove a retriangulated revision.

The required resolver must preserve `(image_id, point2d_idx)` for triangulation and reconstruct BA observations from the surviving v3 `(image_id, point3d_id)` tracks. No duplicate triangulation/reprojection math is justified.

## 11. Bundle Adjustment

**NOT PROVEN with an actual backend through P3.1.** The current golden injects `StubOptimizer`, which copies geometry and sets trace fields (`tests/unit/test_p3_sparse_correction_pipeline.cpp:123-150`). The CLI has no BA provider. The runner passes an empty observation list.

The actual `ColmapBundleAdjustmentAdapter` evaluates source and output geometry via canonical `EvaluateReprojection` (`adapters/colmap/colmap_bundle_adjustment_adapter.cpp:149-154,277-298`). This is the existing path to wire, not a replacement RMS calculator. The current BA probe merely shifts point x by 0.5 (`tests/unit/colmap_probe_shim_main.cpp:240-247,296-305`), so it is not a geometric optimization proof. Native backend compatibility/execution is not established by this audit.

## 12. D5

Required: `rms_after < 0.9 * rms_before`, with both values measured on the same pinned observation set. The existing host-stage gate is present (`engine/pipeline/bundle_adjustment_optimize_pipeline.cpp:125-147`), but the P3.1 golden's trace is supplied by a stub. **NOT PROVEN:** measured full-chain BA improvement.

On N1, retaining the valid v3 is required; no v4 row/artifact or v3 supersede may occur. This is not a requirement to erase earlier successfully committed stages.

## 13. CAS Lineage

**NOT PROVEN for the full chain.** Current goldens check terminal `Has(hash)` and parse a reconstruction document. They do not verify all intermediate feature/calibration/metric/trajectory/revision references or the complete lineage.

Scale eligibility is provenance-derived (`core/trajectory/metric_basis.h:3-14`). `ValidateMetricBasis` only checks nonempty strings (`:88-103`); host resolution and evidence authentication remain required. A caller-provided declaration is not proof that metres exist.

## 14. DB Transaction

**NOT PROVEN for all required transitions and failure cases.** The BA wrapper transaction protects its insert/supersede pair (`bundle_adjustment_optimize_pipeline.cpp:139-147`). The runner commits the source earlier and publishes the final CAS payload after BA persistence. Closure/graph/result writes are also separate in existing lower-level helpers.

The existing `WriteTransaction` starts `BEGIN IMMEDIATE` and does not support nesting (`core/storage/metadata_db.cpp:1830-1868`). A continuation must define host transaction ownership and publication/recovery boundaries, then inject a failure after writes to prove rollback through the production path. Legitimate execution/audit/quarantine records must be distinguished from forbidden partial successful reconstruction revisions.

## 15. Revision Lineage

**NOT PROVEN for the required v2/v3/v4 chain.** Current tests assert only two reconstruction rows (`tests/unit/test_p3_sparse_correction_pipeline.cpp:256-272,309-320`). No retriangulated v3 exists. Successor provenance, complete CAS references, revision timestamps and no divergent replay revisions remain to be proven through the completed pipeline.

`QueryLatestReconstructionByScene` filters succeeded rows (`core/storage/metadata_db.cpp:1904-1911`). N6 must inspect the all-status history before any mutation; checking the status returned by that filtered query is insufficient.

## 18. Determinism

**NOT PROVEN.** Existing goldens invoke the pipeline once; observing a seed at a stub is not double-run evidence. `CachePolicy::kNever` prevents serving a host task from cache, but does not make writes idempotent. Re-running the same source currently risks duplicate reconstruction insertion (`engine/pipeline/sparse_correction_orchestrator.h:70-77`).

The required second `RunPipeline` must compare contractual artifacts, provenance, trajectory/pose values and lineage, demonstrate applicable pure-stage cache hits, and avoid extra divergent revisions. Fresh UUIDv4 instance identities cannot be changed to content IDs merely to satisfy a test. Persisted-operation reuse and independently repeated numeric computation are distinct proofs; neither may be claimed from the other.
