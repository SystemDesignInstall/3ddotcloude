## 1. Outcome

P2.3 closes the processing vertical slice: a session's observations are resolved
to their image content hashes (`SceneQuery`), the single-stage
`feature_extraction` pipeline derives a canonical **FeatureArtifact**
(`feature.schema.json`) behind the worker boundary, and the session layer
records the per-frame `feature_sets` row — the first produced (non-imported)
scene data in the platform.

```
ImageArtifact → SceneQuery.ArtifactHash → feature_extract (worker)
             → FeatureArtifact (CAS) → WriteFeatureArtifact → feature_sets
```

End-to-end verified through `spatial run feature-extraction --session <uuid>`:
per-observation batch continuation (ADR-014), stable `feature_set_id` on
re-execution, CAS dedup, and per-observation failure semantics with non-zero
exit on any failure.

**Finding #1 (gap, MUST):** `ArtifactManifest.configuration_hash` was never
populated by the engine (the image importer populated it; feature artifacts did
not). Closed by M1 (§6).

**Finding #2 (nuance, documented):** `WriteFeatureArtifact` is a scene-aware
writer hosted in `engine/pipeline/feature_extraction.cpp` but called only from
the session/CLI layer. This is intentional (ADR-038: the engine stays
scene-agnostic; the payload writer is shared, the feature_sets row is
session-owned). The header comment documents it as a session-facing helper
hosted in the engine lib.

## 6. configuration_hash provenance (M1 fix)

The ADR-020 cache key is `Sha256Hex(task.config_json)`, where `task.config_json`
is the canonical effective stage configuration (`{"pipeline_id", "pipeline_version",
"stage", "config"}`) built by `PipelineCompiler`; the scheduler forwards exactly
that string to the worker as `TaskRequest.config_json` (`scheduler.cpp`). M1 makes
the artifact manifest record that same digest:

- `WriteFeatureArtifactInput.configuration_hash` added; `WritePayload` writes it
  to `manifest.configuration_hash` (`artifact-manifest.schema.json` allows
  `string|null`; empty serializes as `null`, the parser tolerates null).
- Worker path (`mock_pipeline_runner.cpp`): `input.configuration_hash =
  Sha256Hex(request.config_json)` — identical to the cache-key config digest.
- Session path (`cli/main.cpp`): copies `configuration_hash` from the
  worker-produced FeatureArtifact manifest, so the two artifact instances of
  the same run carry identical provenance (CAS re-Put dedups to the worker's
  manifest on disk either way).
- Round-trip is verified against the **persisted** manifest
  (`artifacts/<uuid>/manifest.json`) via `ArtifactManifest::Read`, plus a
  config-sensitivity check at the CLI level.

The next step is a **decision gate, not code**:

1. **M1** (this review + configuration_hash) — done.
2. **M2** — `docs/development/processing-reconstruction-matrix.md`: capability →
   candidate backend matrix (COLMAP/OpenMVS/GTSAM/Ceres/Open3D/KISS-ICP/VGGT/
   LingBot-Map/gsplat/Nerfstudio) with class separation (no cross-class "who is
   better"), the Robbyant decision gate (Actual output → Canonical Artifact
   feasibility → Metric/relative → Coordinate frame → Confidence → Temporal
   consistency → Classical geometry coexistence; no AI advantage), and a
   recommendation. License signals already surfaced by the schemas gate: OpenMVS
   AGPL-3.0, VGGT conditional, LingBot-Map unspecified, FFmpeg/LASzip LGPL.
3. **M3** — RFC-0008 in `spatial-rfcs` ratifies the chosen backend and the
   `core/plugin/**` / `adapters/interfaces/**` build. No production backend code
   before ratification: the backend choice may change the capability contract,
   adapter interface, artifact contract, runtime/resource requirements, GPU
   model, configuration/provenance, and failure semantics.

## 11. Decisions carried forward

- **Worker owns artifact provenance; session owns scene rows.** The canonical
  payload writer is shared so worker and session produce byte-identical
  artifacts; `configuration_hash` is sourced from the worker's effective stage
  config and copied by the session layer.
- **Effective configuration is the cache-key contract.** `config_hash` (user
  config) and `configuration_hash` (effective stage config) are distinct and
  both persisted (`execution_manifest.config_hash` vs
  `artifact_manifest.configuration_hash`); consumers must not conflate them.
- **No backend code before RFC-0008.** `adapters/*` stay placeholder dirs;
  capability taxonomy extension is RFC-only (worker-capabilities schema).
- **The Robbyant gate is ordered and AI-neutral.** It evaluates a candidate on
  whether its output fits canonical artifacts and can be checked/refined by
  classical geometry tooling (GTSAM/Open3D/COLMAP); it never grants an AI
  advantage.
