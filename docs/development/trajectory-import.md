# Импорт траектории камеры

Команда `spatial import-trajectory` сохраняет файл поз камеры и связывает его
с кадрами существующей сессии. Результат — исходные байты, конфигурация импорта
и каноническая траектория в CAS, а также запись траектории в базе проекта.
Публичная схема `trajectory.schema.json` используется без расширений.

```text
spatial import-trajectory trajectory.txt --format tum --session <UUID> --sensor <UUID> --coordinate-frame slam_local --source-unit meters --clock-domain platform --pose-frame camera --project demo.spx
```

До запуска в проекте должны существовать сессия, камера и кадры с её
временными метками. Замените UUID и имя локальной системы координат на свои.
`--project` указывает на существующий `.spx`. Команда не создаёт кадры и не
изменяет изображения; на стандартный вывод она возвращает JSON с UUID и
SHA-256 импортированных объектов. Повтор того же импорта с той же версией
импортёра возвращает те же UUID и `reused: true`.
Если известны программа и её версия, их можно указать через
`--source-producer <name> --source-version <version>`; это сохраняет сведения
оператора, но не подтверждает подлинность источника.

Поддерживается текстовый формат TUM: одна поза в строке, комментарии начинаются
с `#`; поля разделяются пробелами или табуляцией.

```text
# timestamp_seconds tx ty tz qx qy qz qw
1700000000.123456789 0 0 0 0 0 0 1
1700000000.124456789 3 4 0 0 0 0 1
```

Порядок и смысл полей соответствуют [описанию TUM RGB-D](https://cvg.cit.tum.de/data/datasets/rgbd-dataset/file_formats): положение оптического центра камеры
и её ориентация в неподвижной системе координат. Здесь входной transform —
`T_trajectory_camera`; поворот задаётся quaternion `(x,y,z,w)`. Вход с другой
системой отсчёта, например с позой IMU или LiDAR, требует отдельного
откалиброванного преобразования и не должен выдаваться за позу камеры.

Каждая временная метка должна соответствовать ровно одному кадру выбранной
камеры в выбранной сессии. Значение секунд переводится в целые наносекунды
десятичной арифметикой; ненулевая точность меньше наносекунды, отрицательное
время, переполнение, неупорядоченные или дублирующиеся моменты отклоняются.
Допускается научная запись чисел. Ошибка соответствия, нечисловые значения,
лишние поля и quaternion с длиной, отличающейся от единицы более чем на 0,001,
останавливают импорт до публикации. Quaternion в пределах допуска приводится
к единичной длине; оригинальные байты остаются доступными в CAS.

Параметры единиц, системы координат, домена времени, идентичностей сессии и
камеры, соответствия кадрам, программы-источника и версии импортёра сохраняются в отдельном CAS
артефакте конфигурации. Его хэш и хэш исходного файла входят в provenance
артефакта траектории. Проверяются уже существующие CAS данные; общий исходный
payload переиспользуется без замены существующего индекса артефакта.

## Границы текущей реализации

- `--source-unit meters`, `--clock-domain platform` и `--pose-frame camera`
  — обязательные декларации оператора. Совпадение чисел времени само по себе
  не доказывает синхронизацию камер и SLAM, а обозначение метров не доказывает
  физический масштаб. Траектория сохраняется с `validation_status=unverified`,
  её `metric_basis` не объявляется.
- Импорт не регистрирует преобразование между `slam_local` и системой
  реконструкции, не оценивает неопределённость и пока не подключает сохранённую
  траекторию к `p3_sparse_correction`. Это отдельные этапы.
- Текущий `p3_sparse_correction` всё ещё принимает inline-декларацию
  метрической основы из конфигурации без проверки физического источника.
  До внедрения проверяемого scale evidence нельзя считать этот путь
  подтверждением метрического масштаба.
- Проверка входа выполняется до записи. Записи индекса артефактов и
  траектории сохраняются одной транзакцией SQLite. Файлы CAS публикуются по
  существующему механизму; восстановление после сбоя между записью файлов и
  фиксацией транзакции остаётся открытым вопросом P3.1.

Текущие тестовые наборы синтетические; проверка native SLAM и реальной съёмки
должна быть выполнена отдельно.
